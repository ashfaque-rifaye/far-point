# Phase 1 feasibility spike: preregistration

Written before any spike measurement was run. The thresholds below are copied verbatim from the build brief. Results go to `eval/SPIKE_RESULTS.md` and raw metrics to `results/`.

## Thresholds (verbatim)

- S1 (text decisions): on >= 60 labeled SYNTHETIC states (rendered facts in words + doctrine; Decider never does arithmetic, code computes the numbers), next_action agreement >= 85%, and a 3-4 question request <= 600 ms p50 on this RTX 4060 laptop GPU. (Precedent: 184 ms median for 2 short questions on the same class of GPU, native Windows, no WSL.)
- S2 (image mode): start the server with --vision; on >= 40 labeled webcam frames, glasses_on and looking_far_away accuracy >= 85%, <= 1.5 s per request, and it must fit in VRAM alongside the app.

## Decision rule (verbatim)

- If S2 fails or does not fit VRAM: run Decider TEXT-ONLY (all perception from MediaPipe + foreground-window context) and keep going.
- If S1 fails: tune question wording/criteria (explicit true/false criteria matter) and option descriptions, re-run ONCE, then proceed with the best version and report honestly.
- If the GPU path fails entirely: fall back to CPU (slow) and report it. Do NOT stall.

## How each number is measured (fixed before running)

Model: `StrandsAgents/strands-decider-2B-qwen3.5-v1-2610`, served by `strands-decider serve` on 127.0.0.1:8099, `--device cuda`. Every call goes through the lock in `farpoint/decide.py` (upstream issue #17), so requests never overlap.

### S1

- Test set: 72 synthetic states (8 per next_action label, 9 labels), generated by `eval/s1_states.py` with seed 1. Each state renders the user's doctrine plus measured facts in words. Code computes every number and comparison (for example "32 cm, 8 cm closer than your 40 cm minimum: too close"). Labels come from the doctrine rules in code, not from the model.
- Request: one POST with 3 questions over the rendered state: `next_action` (choice, 9 options with criteria), `strain` (score: relaxed / mild / strong), `interrupt_ok` (noul with explicit true/false criteria).
- Agreement: share of states where the argmax of `next_action` equals the label. Pass needs >= 85% (>= 62 of 72).
- Latency: client wall-clock time of the full HTTP round trip, measured after 5 warm-up requests that are not scored. Pass needs p50 <= 600 ms. p90 and the server-reported `latency_ms` are also reported.
- `strain` (expected level rounded to the nearest level) and `interrupt_ok` (P(true) > 0.5) accuracy are reported but do not gate.
- Retune rule: if S1 fails on agreement, wording and option criteria are changed once after reading the run-1 confusion matrix. The re-run is scored on a fresh 72-state set (seed 2), so the second number is not fitted to the items it was tuned on. Both runs are reported.
- Latency fixes allowed without counting as a retune: runtime configuration only (kernel packages such as `triton-windows` / `flash-linear-attention` / `causal-conv1d`, server flags). Every configuration tried is reported with its numbers. Closing unrelated GPU apps is allowed and reported.

### S2

Measured in this order. A step that fails ends S2 as FAIL.

1. VRAM fit. Restart the server with `--vision`. "Fits alongside the app" means: peak total dedicated GPU memory in use (nvidia-smi, all processes) during the S2 requests is <= 7.4 GB of the 8.0 GB card, which leaves >= 0.6 GB for the dashboard browser and OS. The vision server's own footprint (total used with it loaded minus total used with no Decider loaded) is also reported. A CUDA out-of-memory error is a FAIL.
2. Latency. Request = one webcam frame (resized by the server to 448 px long side) plus 3 noul questions: `glasses_on`, `rubbing_eyes`, `looking_far_away`. Client wall-clock, after 3 warm-up requests, over >= 40 requests. Pass needs p50 <= 1.5 s; p90 is reported too.
3. Accuracy. >= 40 webcam frames with ground-truth labels for `glasses_on` and `looking_far_away`, captured in a guided session (the person poses on a prompt, and the prompt is the label). Pass needs >= 85% accuracy on each of the two questions separately (P(true) > 0.5 counts as true). `rubbing_eyes` and `video_call_on_screen` are reported but do not gate.
   - If nobody is available to pose for labeled frames, S2 accuracy is recorded as NOT MEASURED. Unmeasured counts as not passed, so the decision rule's "S2 fails" branch applies (text-only). Frames are never written into the repository; only aggregate numbers are.

### Mode decision

- S2 PASS and S1 PASS: image mode on.
- S2 FAIL / NOT MEASURED / does not fit: Decider text-only.
- GPU path fails entirely: CPU fallback, reported with its latency.
- S1 FAIL after the one retune: proceed with the better of the two versions and report both numbers.

## Outcome

Recorded after the runs. Details are in `eval/SPIKE_RESULTS.md`.

- S1: FAIL. next_action agreement was 68.1% on run 1 (v1, seed 1) and 68.1% on the one retune (v2, held-out seed 2), against a target of 85%. Latency PASSES at 490 ms p50 for 3 questions. Getting there took two runtime changes allowed above: the triton-windows + flash-linear-attention kernels and High process priority. Before them it was 860 ms.
- S2: VRAM fit PASS (peak 6560 MiB of a 7577 MiB limit). Latency PASS (0.51 s p50). Accuracy NOT MEASURED, because nobody was available to pose for labeled frames. Unmeasured counts as not passed.
- Mode decision: **Decider TEXT-ONLY.** The GPU path works, so the CPU fallback was not needed. Per the S1 rule, the build proceeds with the better question version (v2), and the agreement shortfall is reported as measured.
